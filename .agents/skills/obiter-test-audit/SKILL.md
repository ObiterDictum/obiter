# Obiter Test Audit

Improve confidence per unit of test cost, not the number of lines deleted. A passing suite is not proof that its assertions can catch the claimed bug; a slow or source-inspecting test is not automatically disposable. This skill does not authorise deletion, a PR, a shared-data mutation, or a broad campaign beyond the user's task.

Read `AGENTS.md`, `RULES.md`, and `TESTING.md` before changing tests. Use the current checkout's `package.json` and CI workflow for Bun commands; do not revive pnpm or Vitest instructions. If the task is a PR review or code change, also use the corresponding Obiter review or code-quality skill.

## Choose the mode

- **Author or review a test:** apply the value and failure gates below to the tests in scope. Do not turn an ordinary feature task into a repository-wide audit.
- **Targeted audit or test-speed task:** discover read-only, rank a few candidates by measured cost and confidence, then edit one coherent owner boundary only if evidence is sufficient.
- **Whole-subsystem campaign:** only when explicitly requested. Read [references/campaign.md](references/campaign.md) before inventory or edits. A broad deletion count is never the objective.

## Value and failure gates

For each new, changed, or proposed-for-removal test, identify:

1. The observable behaviour or independent contract it owns, and the credible regression that would make it fail.
2. Its **primary owner boundary**: the nearest meaningful API, UI, database, worker, file, or build-artifact boundary. A lower-layer test may stay when it catches a distinct parsing or state-transition failure; a higher-layer test may stay when it catches transport, lifecycle, permissions, packaging, or persistence that the owner test cannot.
3. What existing test already covers that contract, if any. Compare assertions and failure paths, not names or test counts.
4. Whether the test needs an export, reset hook, flag, mock path, or wrapper with no production caller. Prefer exercising the real boundary; do not create a production seam solely to make a weak test easy.

For a **bug regression**, show it fails on the pre-fix code for the intended reason and passes after the fix. If safe reproduction is unavailable, state the gap rather than claiming fail-first proof. For a new feature, establish an independent expected result; do not calculate the oracle with the code under test.

For a negative auth or isolation case, prove the neighbouring allowed case also succeeds with a real session. An expected 401/404 can otherwise pass because the API is down, the session is invalid, or the fixture never reached the intended permission check.

Treat these as candidates for repair or consolidation, **not automatic deletion**: assertion-free probes; self-comparisons; copied source/import/export lists; assertions on private call shapes already covered through behaviour; duplicate scenarios at the same boundary; expected values generated by the tested helper; mocks that implement the asserted behaviour; negative cases rejected by an unrelated guard; and tests whose title promises more than the assertion proves. When a static assertion protects a real external contract - such as a Docker stage, emitted manifest, CSS source set, migration, or release artifact - keep or strengthen it rather than dismissing it as a grep.

## Obiter retention bar

Do not remove a test's only independent proof of any of these without an equivalent keeper demonstrated at the owning boundary:

- real-session authentication, `/api/me`, permissions, and organisation/matter/user isolation, including negative API paths;
- immutable document versions, soft delete/restore, transactions, idempotency, audit records, and storage-key scope;
- legal-source provenance, citation/quotation/verification correctness, conservative uncertainty, and redaction save/export behaviour;
- web/desktop parity, Electron IPC boundaries, accessibility and keyboard behaviour, SSR assets and private-response caching;
- native ONNX inference and degraded-mode signalling, Bun serving and packaging, and the tested Node API rollback;
- migrations, public contracts, deployment configuration, CI/release gates, and intentionally isolated end-to-end journeys.

This list is a risk map, not a demand to duplicate each scenario at every layer. Preserve distinct failure modes, not duplicated choreography. A baseline failure may be a product bug; investigate it before deleting or skipping the test. Never use real client documents as fixtures or expose private text, credentials, or tokens in assertions, failure messages, screenshots, or logs.

## Targeted audit and performance work

Discovery is read-only first. Pin the assessed commit and inventory the relevant test files, their production owners, direct callers, sibling tests, CI routing, and why each candidate was introduced. For dependency-backed behaviour, inspect the dependency's actual contract. Record a candidate only with: exact test and location; what it can fail on; keeper test and its different or identical failure mode; non-test callers of any seam; history; proposed action (**retain, fix, consolidate, delete**); risk; and focused validation. Missing evidence means retain pending investigation.

For a speed claim, measure wall time and per-file or per-package cost under comparable conditions. Separate Bun startup, `--isolate`/jsdom cost, database setup, test body, and CI scheduling when possible. Keep the same Bun pin, test database, host contention, cache state, and suite selection; use repeated runs sufficient to distinguish gain from normal spread. A CI sample on a different runner is not a local speedup proof. Do not remove `--isolate` without proving equivalent mock/file isolation; do not skip tests, lengthen timeouts, or replace real boundary tests with self-fulfilling mocks to make a number improve. Fix a measured bottleneck before pruning unrelated tests.

Make one coherent change at a time. If consolidating or deleting coverage, name the keeper and deliberately perturb the relevant production behaviour in a disposable checkout where safe; the keeper must fail for the intended reason, then restore the source exactly. Do not mutate shared databases, live services, or private data to validate a test. If such a proof is unsafe, use a narrower synthetic boundary or report the limitation. Run focused owner and sibling tests, then the applicable Bun gates from the current package scripts; check formatting, typecheck/lint, `git diff --check`, and the changed test inventory. Keep test and production/tooling line changes separate in the report.

## Handoff

State the assessed SHA and environment, what contracts changed or stayed protected, which candidate tests were retained and why, any fail-first or deliberate-mutation proof, exact commands and pass/fail/skip results, and remaining gaps. For performance work, report before/after samples and spread, not only a percentage. For an audit, report the keeper for every removed contract. Stop without deletion or PR when evidence is insufficient.
